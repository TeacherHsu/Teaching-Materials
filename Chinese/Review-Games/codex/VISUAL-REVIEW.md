# 綜合複習遊戲 3D 視覺嚴格審查

審查日期：2026-10-16。範圍：大富翁、蛇梯棋、哆寶、賓果、課文偵探密室。參考：`Chinese/Shape-Run-G6A/index.html`。

## 1. 審查結論與證據界線

**五款目前均未達 CF 指定的跑酷美術標準。** 四款棋盤已有立體幾何與部分動畫，但場景還沒有把「看見目標 → 操作 → 世界發生變化」串成完整體驗。密室較有敘事基礎，卻把重要物件藏在標記下面，部分機關動畫又在視窗後播放，甚至在房間重建時消失。繼續堆泛光、彩紙或多邊形，無法修好這些根本問題。

推薦方向是「同一間閱讀探險工作室裡的四套桌遊＋一間可調查的房間」：有一致的材料、光源、道具比例與視覺語言；每款保留自己清楚的玩法與目標。跑酷值得移植的是完整的視覺因果與節奏，不是它的速度。

### 證據與嚴重度

- **[圖]**：使用者提供的五張 1366×900 截圖，來源 `/tmp/rg-shots/v-{monopoly,snakes,dobble,bingo,detective}.png`。直接判斷構圖、遮擋、層級；不以靜態圖判定動畫流暢度。
- **[碼]**：本機實作確認。下列行號是本次版本的定位輔助，函式名稱才是後續工程定位依據；沒有執行 git，也沒有核對遠端版本。
- **[待測]**：合理風險或建議驗收目標，尚未以瀏覽器錄影或 iPad 實測證實。SwiftShader 畫面不能當成真實 GPU 幀率、抗鋸齒或功耗結果。
- **P0**：先修；影響必要資訊、可操作性、降級契約或顯示與規則的一致性。
- **P1**：達到本次美術標準必做；涉及構圖、空間可信度、視覺因果、主要動畫與效能架構。
- **P2**：基礎合格後的細節修飾，不能拿來替代 P0／P1。

## 2. 跑酷為什麼相對合格：可移植技法

以下均來自跑酷現有程式。它並非所有無障礙／效能條件都可直接照搬，也沒有完整電影式劇情；它成功建立了「小黑在黃昏城市收集正確語詞」的可辨識情境。

| 技法 | 實作證據與實際數值 | 移植方式與界線 |
|---|---|---|
| 明確主角與行動目的 | 標題／說明約 L176；`dog` 群組約 L492；收集目標與 `buildSlots()` | 讓玩家知道自己在完成什麼。棋子仍保留隊伍顏色＋形狀＋號碼；可增加共同導覽角色或工具，不改計分與勝負。 |
| 選單構圖與遊戲鏡頭分工 | `loop()` L886–892：選單相機目標 `(-.6,2.4,7.4)`，遊戲跟隨 `(dog.x*.55,4.6,9.2)`；`lookAt` 將選單主角留右、標題留左 | 桌遊先做好固定遊玩鏡頭，再做可跳過的單次入場。作答中不能持續環繞、追逐棋子或改變字級。 |
| 有阻尼、沒有鏡頭噱頭 | `position.lerp(want,min(1,dt*2或4))`；一般 FOV 58，直向 72；實際迴圈固定 FOV，**沒有衝刺變焦或震動** | 移植有界、一次性的構圖轉換。若用持續阻尼，建議 `1-exp(-lambda*dt)`、`lambda=6–10`，並在誤差夠小時停止排幀。 |
| 背景有前、中、遠景 | 跑道、女兒牆、路燈、近樓、遠方剪影；`Fog(0xd98a78,90,280)` | 桌遊建立「桌緣／棋盤／低對比背景」三層。不是複製 90–280 的霧距到只有十幾單位的棋盤，也不必另造整座城市。 |
| 色光有方向與分工 | `HemisphereLight(.85)`、暖主光 2.0、紫冷補光 .55；陰影 1024；天空 shader 漸層與太陽方向一致 | 採一個主光、一個弱補光、低強度環境光。密室窗戶與投影方向要能互相解釋；不要用均勻白光抹平所有面。 |
| 材質會回應環境 | L330 起 Canvas 512×256 全景 → `PMREMGenerator` → `scene.environment`；金幣邊 `metalness=1,roughness=.22`；道路 `.8/.05` | 程序環境圖只生成一次，使用木、紙、布、漆、金屬不同參數。避免所有東西共用「有點亮的塑膠」。 |
| 細節服務尺度 | `roadTexture()` 的細顆粒、車道線；`windowTexture()` 規律窗格、只有約 15% 亮窗，建築頂面與側面分材質 | 用低對比、低頻程序紋理補材料感。書脊、桌緣、紙張厚度都比把每個圓柱從 20 面升至 80 面有效。 |
| 角色有動作層次 | `loop()`：四腳對角交替、身體起伏 .14、換道側傾、耳尾次級動作 | 棋子移動可有起步、抬起、落地；只動當前棋子。桌面回合遊戲不需要所有角色永遠呼吸、搖擺。 |
| 閱讀與運動分相位 | `beginRead()`／`endRead()`；`sp` 在判讀／訂正時為 0；金幣不漂浮、不旋轉 | 題目、詞義、線索出現時固定場景與 DOM。環境動畫不能與閱讀競爭；保留逐格步數與既有朗讀節奏。 |
| DOM 與空間有對應 | `showStrip()` 的三欄對應三條跑道；字面材質不受光洗白；主要語詞另有 DOM | 棋盤 DOM 標籤、詞槽、隊伍狀態要有固定視覺錨點。不能因「更像 3D」把題目轉為 Canvas-only。 |
| 回饋有對象與結尾 | `burst()` 用 `Points`；`ring()` 短生命週期；`finish()` 只播 24 粒／.6 秒、其後出成果 | 改變成功物件或已有進度，局部一次 8–16 粒已足夠。一般答對不應每次炸滿場彩紙。 |
| 克制環境刺激 | `dust.visible=false`；亮窗稀疏；bloom 強度 .15；金幣穩定；減少動態抑制 burst | 「細緻」不等於更多運動。桌遊預設不開漂浮光塵、循環脈動、鏡頭抖動、全場發光。 |
| 時間步與資源有基本紀律 | `dt` 限 .05 秒；樓房循環使用；粒子到期 dispose；DPR 上限 1.6 | 棋盤現有按需渲染應保留。不要為抄跑酷的常駐 `requestAnimationFrame` 犧牲桌遊的閒置效率。 |

**不可直接移植**：跑酷的倒數、時間顯示、失敗淘汰、趣味排泄物、外部 Google Fonts、常駐奔跑場景與任意全畫面特效。它的隱藏光塵仍有更新程式，角色部分次級動作也不全由減少動態控制；這些不是範本。只選適合本案約束的技法。

### 3.2 建議的材料、光照、鏡頭與 UI 基線

以下是**調整起點與驗收目標，不是已實測最佳值**。世界單位沿用現有棋盤格距 1.8、密室寬 12。

| 項目 | 建議實作 |
|---|---|
| 色彩流程 | 棋盤保留 `outputEncoding=THREE.sRGBEncoding`、ACES、exposure 先用 .95–1.0。密室補同一流程。CSS hex／程序 Canvas 色彩先約定 sRGB 輸入，材質色轉 linear 一次；CanvasTexture 設 sRGBEncoding。不可混用現代版本的 `outputColorSpace`。 |
| 材質類型 | 木：roughness .72–.85、metalness 0；紙：.9–1／0；布：.95／0；漆面棋子：.35–.45／0；黃銅：.3–.4／.65–.8。成功色使用既有隊伍色 token；課次色不兼作所有權色。 |
| 環境圖 | 自製 256×128 或 512×256 室內漸層 Canvas，不放文字、不抓外部圖片；`PMREMGenerator.fromEquirectangular()` 產一次。保留 render target 供最後 dispose，生成器與來源紋理完成後釋放；低階可省略。 |
| 光影 | Hemisphere .35–.5、暖主光 1.0–1.2、冷補光 .2–.35；先減少洗白再調曝光。1 個 shadow light，1024 起；棋盤 shadow camera 收到約 ±7、依動畫包圍盒驗證。低階 512 或關陰影，以程序接觸陰影補足。 |
| 程序紋理 | 木紋 256–512，亮暗差約 5–8%，不用粗密平行掃描線；棋盤與桌面紋理比例不同。布面微紋只在近景可辨。重複物件共享 map／geometry／material。 |
| 鏡頭 | 棋盤 FOV 32–36、俯角先試 58–62°，改善遠近格差；DOM 字不跟世界距離縮小。`resize()` 計算玩法物件包圍盒，排除 40×40 桌面，納入骰子最高點與 DOM 標籤像素邊界，四邊至少 16–24px。 |
| 動作 | 一般落子 320–420ms、單次翻／滑 220–360ms；無 overshoot 的 smoothstep 或 easeOutCubic。教學逐格移動保留現有 560ms 節點和朗讀，不藉美術任務縮短。裝飾回饋不強迫等候、不搶焦點。 |
| 文字 | 一般教學／選項 24–32px，投影 32–38px；格號／課次不低於 22px；輔助資訊至少 18px。主要操作區 ≥48×48 CSS px，間距 ≥8px。這是設計目標，長文寧可重排／捲動，不縮字。 |
| 對比 | 文字以實際前景／背景驗算至少 4.5:1；必要非文字狀態與焦點邊界至少 3:1 作本案驗收門檻。深棕字配不透明淺紙底，隊伍顏色外加形狀／編號；不能只看截圖猜對比達標。 |
| UI 層級 | 一個當前任務、一個主操作、相鄰的簡短結果；教師畫面設定可收合，仍能鍵盤開啟。取消面向學生的「3D 立體視圖」大橫條作主視覺，改為小型畫面設定入口，2D 降級原因仍可讀。 |

Three r128 API 已以固定版本的官方原始碼核對：`WebGLRenderer` 提供 `outputEncoding`／`toneMapping`／`setPixelRatio`，不要使用新版本色彩 API。[r128 WebGLRenderer](https://raw.githubusercontent.com/mrdoob/three.js/r128/src/renderers/WebGLRenderer.js)

程序環境預濾與重複模型實例化可使用核心內的 `PMREMGenerator`、`InstancedMesh`；不需要另引大型套件。[r128 PMREMGenerator](https://raw.githubusercontent.com/mrdoob/three.js/r128/src/extras/PMREMGenerator.js)、[r128 InstancedMesh](https://raw.githubusercontent.com/mrdoob/three.js/r128/src/objects/InstancedMesh.js)

後續執行時只載入 cdnjs 的 `three.js/r128/three.min.js`；若保留既有後製，限 jsdelivr 的 `three@0.128.0/examples/js/` 相依檔。上述原始碼連結是審查參考，**不是新增執行期依賴**。

### 4.2 可實作方案

估工以熟悉 Three.js 的單一工程師、1 人日＝8 小時計；以下不重複計共用 C 項。

| 工作包／級別 | 檔案、函式與做法 | 參數／驗收 | 估工 |

### 8.3 密室動畫接線契約

機關成功已由 `C.check()` 決定；視圖只接收成功結果。建議資料流如下，**不要把動畫完成當作答對的條件**：

```text
既有 C.check / C.investigate 更新遊戲狀態
  → DOM 立即顯示原有回饋、記錄照舊
  → 由 solved / found 產生唯讀視覺 snapshot
  → 關閉原有視窗時，選擇播放對應物件的一次動畫
  → 動畫完成／略過／失敗／切 2D，全部收斂到同一模型終態
```

`Room` 可以保存演出佇列、快照與資源，不能自己呼叫 `C.check()`、重抽題、重寫學習紀錄。關窗後的回饋可隨下一個操作立即取消。逃出保留既有成功條件與結果內容，只修正 `play()` 重建造成的門動畫失效；不新增一道必須作答的開門操作。

## 9. 效能與低階降級：先有預算，再加美術

### 9.1 三級品質建議

這是交付門檻的起始提案，**本次沒有量測現況 draw calls、GPU 記憶體或 FPS**；各遊戲應先取基線再微調。60fps 是實機目標，不是從程式碼推得的結論。

| 項目 | 高階 3D | 標準 3D（預設） | 輕量 3D |
|---|---|---|---|
| DPR 上限 | 1.5 | 1.25 | 1.0 |
| 陰影 | 單燈 1024，必要時才 2048 | 單燈 1024／512 | 關動態陰影，保留程序接觸陰影 |
| 後製 | 可選，僅回饋期間、半解析度遮罩 | 關 | 關 |
| 背景／細節 | 完整次要道具 | 主題核心道具 | 拿掉不可互動的小擺設，保留任務物件 |
| 粒子 | 一次 ≤16 | 一次 ≤8–12 | 0；DOM 靜態結果照常 |
| 場景主 pass draw calls 預算 | ≤160 | ≤100 | ≤60 |
| 可見三角形起始預算 | ≤120k | ≤70k | ≤35k |
| 動畫與資訊 | 相同規則、相同終態 | 相同 | 相同，不減字／減選項／改盤面 |

雙人哆寶以**兩視圖合計**控制在標準預算附近，不能每個 renderer 都吃滿整個裝置預算。這些數字是上限而非必須用完；密室超額時優先合併靜態書、窗框、地板線與梯子橫檔，不砍互動物件。

### 9.2 明確實作位置

1. **品質管理**：`scene3d.js` `View.init()`／`draw()` 與 `detective3d.js` `Room.init3d()`／`frame()` 新增 `quality`／`applyQuality(level)`。先標準品質，記錄活躍動畫的 rAF 間隔；排除首輪 shader 編譯、背景頁與閒置空檔。連續兩個各 90 活躍幀的視窗 p95 >22ms，降一級；輕量仍持續 >28ms 時轉 2D，DOM 簡短通知且不搶焦點。一局只降不升，防止畫質往返跳動。
2. **渲染按需**：棋盤保留 `draw()` 無 tween 即停止。密室移除所有待機 pulse，`setState()`／resize／拖曳／有限 tween 才 `kick()`；modal 閱讀中不要繼續跑背景粒子。hidden 時完成或取消裝飾補間到正確終態，取消 rAF；回到 visible 只補一幀。
3. **陰影按需**：`mesh()` 不再全部 castShadow=true。大件靜態家具與玩家棋子才投影；骰點、書頁線、足跡、紙片、文字與小旗牌不投。可設 shadowMap.autoUpdate=false，在投影者或光源改變時標記 needsUpdate；靜態讀題期不重算陰影。
4. **物件重用**：`layoutOverlay()` 尺寸沒變不重建；`markCell()` 改材質／矩陣，`drawMatch()` 改線端點。蛇斑點、梯子橫檔、書本用少量共享材質分批 InstancedMesh；任何批次不需要互動 raycast，保留原獨立 hit box。
5. **粒子批次**：兩份 `burst/confetti` 改一組 `Points` 或 InstancedMesh。共用生命週期；raw t 計算軌跡、eased t 只用在 UI 插值。物件池完成後回收，最終 dispose 釋放。不能同時留下多批尚未結束的彩紙。
6. **DOM 測量批次**：`pointAt()`／`layoutMarkers()` 先一次讀所有 rect，再一次寫樣式；不在逐物件迴圈混讀混寫。視角／尺寸不變時不重算標記。DOM 字體載入採系統字，不引入字型網路請求。
7. **完整釋放**：`View.clearGroup()` 區分共享與私有資源；`Room.teardown3d()` 對 geometry、material、map／alphaMap／環境 render target 去重後 dispose，清除 tween 與 mesh 參照、解除 listener／observer。同一局避免反覆建立 context，最終退出才釋放。
8. **量測**：開發驗收可暫時記錄 `renderer.info`、rAF p50/p95/p99、長任務與 heap 走勢。多 pass 要累計各 pass，不能只讀最後一次 render 的 calls。正式學生介面不顯示技術數字，也不送外部遙測。

### 9.3 實機驗收方式

- 指定一台學校實際使用的 iPad（記錄型號、iPadOS、Safari 版本）、一台教室電腦（記錄 CPU／GPU、作業系統、瀏覽器）、一台相對低階裝置。不能用「iPad」三字代替裝置資訊。
- 熱機後各跑約 2 分鐘代表操作：六步移動、重複相同骰點、特殊路徑、連續選格、哆寶雙人配對、密室拖轉／解謎／開門。把閱讀停留與動畫幀分開統計，閒置零幀不能算出高 FPS。
- 60Hz 裝置活躍動畫以接近 60fps 為目標：中位幀距約 16.7ms、p95 ≤20ms、p99 ≤33.3ms 作初始門檻；視覺上無持續拖影式掉幀。若不合格，必須實際觸發降級並重新量測，不寫「應該順」。
- 閒置／讀題 10 秒沒有持續 rAF；回背景再返回沒有卡住或過場突然重播；連續建立／結束 10 局後資源在 warm-up 後不單調增長。要觀察 GC 後趨勢，不用單次 heap 大小下結論。
- SwiftShader 只驗構圖與失敗路徑，不能作效能通過證據。低階 2D 是完整且可交付的保底，不能灰掉主操作要求重新開局。

### 12.2 規則不變的驗證方法

使用測試固定的題庫、設定與遊戲亂數流，對同一段輸入逐步比較改動前後：題目 ID／選項順序、骰點、玩家位置、回合、金錢／owner、各類學習統計、密室 found／solved／hints 與最後儲存紀錄。時間戳與純視覺欄位可排除；其他差異須解釋並修正。新美術亂數不得改變遊戲 RNG。

新增測試集中於真正易失效的邊界：密室載入競態／動態設定變更／modal 後視覺狀態／結果只寫一次，及棋盤骰點重同步、蛇有效路徑。不要替每個顏色常數寫一份鏡像測試。GPU／文字可讀性另用瀏覽器與人工驗收，不能用 mock 假裝測到。

後續工程的基本命令（本次只執行前述 31 項測試，以下是**未來驗收要求**）：

```sh
node --check Chinese/Review-Games/common.js
node --check Chinese/Review-Games/scene3d.js
node --check Chinese/Review-Games/detective3d.js
node --check Chinese/Review-Games/detective.js
node --test Chinese/Review-Games/tests/scene3d.test.cjs Chinese/Review-Games/tests/detective.test.cjs
python3 Chinese/Review-Games/tools/check_data.py
```

四份 HTML inline script 另以暫存檔抽出 `node --check`；既有 `tools/qa/play-*.js` 可當操作素材，但應先檢查它們實際覆蓋的模式，再補測本矩陣。沒有修改跑酷或題庫，不重跑資料生成工具，也不把跑酷改造成這次新規格。

### 12.3 美術退件條件

下列任一成立，不能以「測試都過」交付：

1. 必要題目、狀態或路線仍只能看 Canvas；文字靠縮小才塞得下；底列／主操作被裁切。
2. 只是把 bloom、彩紙、反光或模型數加倍，場景焦點、材質與因果仍不清楚。
3. 詞在原地、底下卡片獨自旋轉；已開機關在下一畫面關閉；畫出的蛇尾與實際落點不同。
4. 讀題時還有循環脈動、全場漂浮、持續相機運動；減少動態只停 CSS 而未回 2D。
5. 只有桌面 SwiftShader 截圖，沒有 iPad／教室電腦成績與降級實證。
6. 美術演出新增一次判分、重抽題、改動計分／紀錄，或因失敗讓原玩法不能完成。

CF 的簽收應使用同一課次、相同狀態的前後截圖，加每款一段 15–30 秒操作錄影；先看「能否立即辨識現在的任務、操作對象與結果」，再看光影與裝飾。跑酷級的完成度來自這些環節同時成立。
